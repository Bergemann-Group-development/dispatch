# Repository guidance

Maintain shared agent instructions here. `CLAUDE.md` links to this file.
Explicit user instructions take precedence.

If in doubt, present a concise multiple-choice question and let the user decide.

## Subagents

Run each subagent in a clean Git worktree on a dedicated branch. When the current
uncommitted work is part of the task context, first capture it in a checkpoint commit
on a temporary integration branch:

```sh
git status --short
git switch -c integration/<topic>
git add -A -- .
git commit -m "WIP: <topic> subagent baseline"
base=$(git rev-parse HEAD)
```

Review the status before staging. The checkpoint is a working baseline and need not be
kept in the final history. If the required baseline is already committed, use that
revision directly instead.

Create every independent subagent worktree from the same baseline:

```sh
repo=$(git rev-parse --show-toplevel)
project=$(git rev-parse --show-prefix)
git -C "$repo" worktree add -b agent/<task> <worktree-path> "$base"
```

Start the subagent in `<worktree-path>/$project`. Its assignment must include the base
revision, branch, owned files or subsystem, expected result and relevant verification.
Tell it to read `SUBAGENTS.md` before working.

Give concurrent subagents disjoint ownership. If tasks touch the same files or one
depends on another, integrate the prerequisite first and create the dependent
worktree from the resulting commit.

Review the returned commits with `git show` or `git diff <base>..<commit>` before
cherry-picking them onto the integration branch. Remove the worktree and task branch
only after the result has been accepted or deliberately rejected.

## Architecture

OpenMULTI3D is under active development, much of it performed by agents.
Responsibilities across its three components are still evolving:

- `SRC/`, the Dispatch entry points and `HOP/` contain the numerical application
  and supporting physics. Dispatch provides task-based parallelisation,
  primarily for 3D radiation-hydrodynamics. OpenMULTI3D uses it for spectrum
  synthesis from hydrodynamic and hydrostatic model atmospheres.
- `tumult/` provides the Python API for reading and visualising outputs,
  launching jobs and numerical analysis.
- `TumultStudio/` is the current GUI and provides interactive spectroscopic
  analysis through Bokeh. Some scientific workflows currently live here.
  `TumultStudio2/` is its predecessor, kept only for comparison, and
  `TumultStudio_old/` is legacy. Neither is a target for new work.

`docs/GUIWorkflow.md` describes the target TumultStudio tool workflow.
`docs/GLOSSARY.md` defines the terms these components share, including the ones that mean
different things in each. Read it before naming anything, and add to it when a name turns
out to be ambiguous. `docs/PythonNamingConventions.md` covers how Python names are spelled;
`docs/F90CodeConventions.tex` is DISPATCH's own, and governs `SRC/` and `HOP/`.

Inspect the relevant code to establish current interfaces. The intended
architecture shares a headless workflow layer between Python callers, the GUI
and a thin MCP adapter. Keep scientific calculations usable without Bokeh or
MCP. Extract workflows as needed for the task, preserving numerical behavior.

## Changes and verification

Search existing code before extending it. Consolidation and new abstractions
are welcome when problems share the same physical nature. Check their units,
assumptions and validity regimes, then give the shared physics one implementation.
Check callers when removing superseded code and keep cleanup within scope.

Additional edge-case handling, options, dependencies and compatibility layers
need a concrete requirement or demonstrated failure. Avoid speculative features
and fallbacks that hide errors. Update existing documentation where practical;
create reports, plans and examples only when the task needs them. Keep temporary
diagnostics and generated outputs out of tracked source files.

The existing `tests/` suite was generated by agents without user curation.
Assess its assumptions before relying on its assertions. Explain conflicts
between tests, implementation and scientific intent. Changes to golden outputs
or assertions need a justification beyond making tests pass.

Run checks suited to the change. Add tests for meaningful
requirements, physical invariants or demonstrated regressions. Avoid tests that
mirror implementation details and speculative edge-case suites. Check content
and links for documentation edits. New reference datasets and broad test-suite
rework require a task that calls for them.

## Development

The local `Makefile` uses `../../config/Makefile` from the parent Dispatch
checkout. Check compiler and host settings before building. Consult
`README_INSTALL.md` and `requirements.txt` for setup, checking that their
instructions fit the current environment. From this directory, use `make` to
build, `python -m pytest tests/<relevant_test>.py` for selected tests and
`bin/tpy -m TumultStudio` for the GUI (`bokeh serve --show TumultStudio` without its landing page). Numerical tests may require
input data and compiled libraries.

Use relative paths or user configuration for machine-dependent locations.
Keep local settings and large datasets out of version control. Check ignore
rules when adding source files: the parent repository ignores many new files
in this experiment.

## Writing

Comments and docstrings should explain current behavior and its rationale.
Update stale descriptions when code changes. File history belongs in version
control; omit accounts of earlier implementations and editing sessions.

Use skills for recurring procedures when useful. Reference maintained code and
documentation, keep executable logic in code and maintain shared policies here.

Apply these rules to agent responses, documentation, reports and other written
products. Avoid repeated em dashes, repeated "X, not Y" formulations, promotional
comparisons, conversational metadiscourse, unsupported universal statements and
rhetorical lists added only for cadence. Keep responses concise by default.
Explain scientific reasoning and verification details when requested or needed
for a concrete decision.

## Python preferences

Use pathlib.Path for file/path work, not os.path string ops.
Prefer intrinsically dimensionless formulations for internal calculations (e.g. photon occupation number instead of intensity), while using astropy.units to convert and scale physical quantities at user-facing boundaries.
